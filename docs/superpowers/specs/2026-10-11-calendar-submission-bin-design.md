## Submission bin
Keep existing links working. Add drafts, multiple links, private file attachments and an optional note. Accepted links include Google Docs, Sheets, Slides and Drive; opening them does not grant the lead access automatically. Explain that the intern must share Google files with the reviewing lead. This change does not include Google Drive Picker or copying files into Drive.
Allow PDF, DOC/DOCX, XLS/XLSX, PPT/PPTX, TXT, PNG and JPG/JPEG. Maximum five attachments, each at most 10 MiB. Enforce extension and MIME allowlists; reject executables/HTML/SVG/archive formats and mismatched allowed types. Do not claim malware scanning is provided.
Existing submission_url becomes optional, with existing values preserved and displayed as the first link. Store additional links and notes in submission content; file metadata records UUID, requirement_id, user_id, original filename, object path, size and MIME. Never use the original filename as a storage key.
Private bucket eif-submissions; objects at userId/requirementId/randomUUID.extension. Only owner and current cohort leads can download. No anonymous reads, public URLs, teammate access or permanent signed links. Downloads use fresh short-lived signed URLs (60 seconds). Responses sanitize filename display and open files separately from the app.
State transitions: draft -> in_review via Submit; in_review -> draft via Unsubmit before cutoff; draft -> in_review via Resubmit. completed/pending remain compatible with existing lead review states. Approved work stays locked unless the lead requests changes before cutoff. At or after cutoff, owner edits, unsubmit, upload, overwrite, attachment deletion and submission removal are rejected. Leads can still approve/request changes but a review alone does not unlock an expired submission.
A requirement due_date locks at the start of the next day in Asia/Manila: Oct 13 permits edits until Oct 14 00:00:00+08:00. Add optional due_at for exact-time deadlines; if set it takes precedence over due_date. No deadline means editable while not approved. A lead can explicitly extend due_date/due_at; show the new cutoff.
SQL guards and Storage RLS enforce ownership, cohort, state and cutoff using database time, including direct API attempts. Unsubmit clears review metadata; resubmit replaces submitted_at and clears reviewed_at. Content and attachments are immutable while submitted; lead review changes only status/review metadata.
Draft creation precedes file upload so Storage policies can validate a submission. Object deletion cannot delete a submitted/expired attachment. Failed upload retains existing content and offers retry; failed finalization leaves a draft and clearly does not report successful submission. Prevent concurrent submit/edit races by serializing content/attachment mutations and finalization on the submission row; never mutate a referenced object in place.
Delete unlinked failed-upload objects only through a server cleanup procedure, never using unrestricted client deletion. Removing a requirement remains lead-authorized and must account for stored objects without leaving an unbounded orphan collection.
Intern UI: add links/files/note, draft badge, Save draft, Submit, Unsubmit to edit, Resubmit, exact Manila cutoff and Locked state. Lead UI: preview metadata, authorized attachment download, links/note and existing review controls. Persist after refresh; retain input on failure.
Assistant may see submission status and attachment names only if needed; never automatically send file bytes or private URLs to OpenRouter.

## Google Calendar
Calendar integration is distinct from fellowship authentication. Each intern and lead connects their own Google account while keeping the existing Supabase login.
Use server-side OAuth authorization code flow with PKCE, offline access, expiring single-use state tied to the Supabase user and a secure HttpOnly SameSite=Lax browser cookie. The callback must validate state, browser binding and provider error before linking. Do not put Supabase access tokens or Google tokens in URLs, logs or frontend localStorage.
Initial scope https://www.googleapis.com/auth/calendar.events plus openid/email to label the account. Sync to the connected user's primary calendar; no calendar-list or Gmail/Drive scope.
Store encrypted Google refresh/access credentials in a non-exposed private schema, server-only. AES-256-GCM encryption uses a server environment key; RLS/grants deny anon/authenticated token access. Server operations use a scoped internal database interface and restricted privileged credentials; verify the Supabase bearer token and current profile before accessing a user's connection. Never allow a client-supplied user ID to choose token ownership.
Routes: POST /api/google/connect returns an authorization URL; GET /api/google/callback validates/exchanges; GET /api/google/status returns connected/email (no credentials); POST /api/google/sync accepts selected source IDs/types; DELETE /api/google/connection revokes and removes credentials. Mutating routes verify Origin against APP_URL, validate bearer tokens and limit request sizes/rates; OAuth callback has state/cookie binding.
Sources: permitted cohort events and requirement deadlines first. Interns sync applicable individual/shared requirements and cohort events; leads sync permitted cohort events/requirement definitions. Backend rereads these records under the user's token and derives title/date/time instead of trusting client event fields.
Show a review screen listing selected records before Sync. Sync writes only the current user's calendar; no attendee invitations or writes to another intern's calendar. Each person connects and initiates their own sync.
Date-only deadlines become all-day entries with exclusive end date the following day. Exact deadlines become 30-minute entries beginning at cutoff; existing events use stored ends_at if present, otherwise visibly labeled default duration 60 minutes. Use Asia/Manila for fellowship timestamps.
Save Google event IDs per user/source with a unique key, source fingerprint and sync timestamp. Derive a stable Google-compatible event ID from user/source to make creation retry-safe even if the mapping write fails. Repeat sync updates the app-managed event when its source changes, otherwise skips it. Never overwrite unrelated calendar entries. User-deleted entries can be recreated only on explicit resync. Source deletions are shown as stale; do not silently delete calendar events in this initial scope.
Return per-item created/updated/skipped/failed results; partial failure must not claim full success. Bound a batch to 20 records. Handle expired tokens by refresh, revoked consent with Reconnect, 429 with retry guidance, malformed provider responses and retries without duplicate events.
Disconnect revokes Google access and deletes stored credentials/state; explain already-created calendar events remain.
UI lives in Calendar: connection status, Connect/Reconnect/Disconnect, selectable records, review and sync results. Assistant can explain/navigate to this flow; direct chat execution is deferred until the verified sync exists and has explicit action confirmation. A model change alone cannot enable it.

## Required configuration
Server-only: GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, GOOGLE_REDIRECT_URI, GOOGLE_TOKEN_ENCRYPTION_KEY, APP_URL, SUPABASE_SERVICE_ROLE_KEY (restricted backend only). Existing Supabase/OpenRouter variables remain unchanged. No VITE_ prefix for any secret.
GOOGLE_REDIRECT_URI must equal APP_URL + /api/google/callback and be registered exactly in Google Cloud. APP_URL is a fixed trusted origin, not derived from request Host headers. Use separate test and production OAuth configuration.
Enable Google Calendar API; configure OAuth consent audience/test users; create a Web application client; register redirects. Google Cloud project/account configuration is performed by its owner; do not ask for credentials in chat.
Connection and synchronization remain unconfigured until those values are supplied securely. Do not expose an apparently working Connect action when server configuration is absent.
Use pinned Google OAuth library version/lockfile after current compatibility checks; avoid writing a custom OAuth protocol implementation.

Run PostgreSQL permission/Storage tests with rolled-back fixtures, frontend/API tests, TypeScript/build and both-role browser walkthrough. Live OAuth requires configured test accounts and explicit user consent; mock tests do not prove the real connection.
Deliver submission feature first, then calendar integration. Both extend feature/week-2-core-build without undoing logo/UI work or merging closed AI Knowledge PR #10. Document exact migrations, environment setup, rollback and manual QA steps; no automatic production migration, merge or deployment.
